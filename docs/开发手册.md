# 开发手册 — 踩坑与解法

本手册记录开发中踩过的坑：现象、根因、解法与可迁移的教训。新条目放最上面。

## 2026-11-08 导出 toast 测试的三连坑

- **现象**：`TestExportFolderToast` 首跑超时，`h.app.toasts` 始终为空；中间一次"偶发"通过后又稳定失败。
- **根因**（三层）：
  1. `fakePlatform.NotificationsSupported` 里 `p.record()` 与随后的 `p.mu.Lock()` 各锁一次 `p.mu`，同线程二次加锁死锁（在 UI 线程上调用即卡死整帧）。
  2. toast 的生命周期只有一帧：`App.View` 把 `a.toasts` 交给窗口后立即清空（shell.go `a.toasts, a.closeToasts = nil, nil`），测试在 `Frame()` 之后断言必然为空。
  3. 测试直接写 `h.plat.dir` 未持锁，与后台 goroutine 的持锁读之间没有 happens-before，读方可能永远看到 ""。
- **解法**：
  - 平台通知放到后台 goroutine（`a.do(...)`，同 mcpsend 的模式），不占 UI 线程；
  - 测试在 `h.drain()` 之后、`h.tt.Frame()` 之前检查 `a.toasts`；
  - 测试写共享字段用 `h.plat.mu.Lock()` 包住。
- **教训**：平台回调（Notify/OpenURL 等）默认不在 UI 线程调用；测试断言"每帧被清空的状态"必须在一帧生命周期内取点；测试里绕过锁直写共享字段是定时炸弹。

## 2026-11-08 Windows 读信页远程图"破图"

- **现象**：农行对账单等 HTML 邮件的远程图（`http://media.abchina.com/...`）全部破图；网易自家域名的图正常。Foxmail 同邮件正常。
- **根因**：用户设置 `RemoteImages: "auto"` 时图都放行，走 `godwit-img` 代理；Windows 上代理 URL 形如 `http://m<id>.godwit-img.localhost/<token>`，由 mygo 的 schemehost + WebResourceRequested 过滤器应答。链路本身是通的（`scripts/imgproto-win` 探针验证，含 sandboxed srcdoc iframe），失败发生在"页面加载时现取现用"的偶发环节；缓存命中的图走 `embedCached` 的 data: 内嵌，从不失败——这正是网易图正常的原因。
- **解法**：根治靠"图在邮件到达/首开时入缓存"；存量邮件可用预热脚本把 body_html 里的 URL 灌进 `D:\godwit\cache\images`。图床已 404（2021 年老模板）或证书过期的无法恢复，考虑渲染占位块。
- **教训**：诊断先分清"拦截"（src 被剥，见 sanitize 的 `finish()`）与"加载失败"（src 在但取不回）；`scripts/imgproto`（WebKit）与 `scripts/imgproto-win`（WebView2）按平台复制场景，不要靠猜。WebView2 下自定义 scheme 子资源必须走 `http://<host>.<scheme>.localhost` 形式（`proxyPrefix` 已处理），页面 CSP 也要放行该形式（`FRAME_CSP`）。

## 2026-11-08 fakePlatform 的锁纪律

- **现象/根因**：见上。`fakePlatform` 的多数方法模式是 `record(...)`（内部加锁）后紧跟手动 `Lock()`，天然是重入死锁陷阱。
- **解法**：新增 fakePlatform 方法时，要么 record 返回后不再加锁，要么不用 record；新增调用点若可能持 `p.mu` 时回调平台接口，先移出。
- **教训**：测试替身的接口契约要与真实实现一致——真实平台的 `Notify` 可以阻塞，但绝不能死锁；替身也应如此。
